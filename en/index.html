Finder learned tabs.
Then it stopped.

SuperFinder finishes the set: an address bar that takes you straight there, search-as-place, a layered bookmarks bar, a start page with recently-closed tabs. If you know Chrome or Safari, you already know SuperFinder — twenty years of muscle memory, reused as-is.

⌘Laddress ⌘Tnew tab ⌘Fsearch

The address bar does three things

Paste a path, hit Return, arrive — the kind you copied out of a terminal or an AI chat. Type ~ and Tab through each level. One click copies the current path. It's all live in the window up top.

Search is a place

Search results aren't a throwaway page — go back in them, bookmark them, restore them. Folders and search results are the same thing here: a Place.

Bookmarks bar & start page

Bookmarks group into folders with icons — as many as you need. ⌘T opens a Safari-style start page; recently closed tabs come back whole.

Close. Return.
Everything's here.

⌘Q and the tab groups, the four-way pane trees, the shelf references — all of it saved. Reopen, and the scene is exactly as you left it. Real browsers restore sessions. So does this.

Whole trees come back

Not just tabs: each pane tree's structure, ratios, and every folder it held — restored together.

Crashes count too

Snapshots land on disk continuously, throttled. A crash gets the same treatment as a clean quit.

A workspace you split —
and get back.

The high-frequency move in heavy file work is compare. In SuperFinder it happens inside the tab — recursive four-way splits, grip-drag swaps — and the scene you built can be named, saved, and restored in a new tab with one click. Dual-pane managers answer “how do I see two folders”. They don't answer “how is my whole workspace saved”.

Recursive splits, in-tab

Right-click the blank, split four ways, as deep as you need; drag a pane's edge grip to swap in place. One window is always one browser — no fixed two-pane frames.

Saved layouts

The ▦ button in the address bar names the split structure, each pane's folder, and its view mode. Click the chip in the bookmarks bar — the same scene reopens in a new tab.

Staging shelf

The tray for cross-tab moves — drop in and it only records a reference, the original stays put; it follows the session and survives restarts; the single move happens when you drag out.

Select. Act in place.

The top half of the sidebar is lean info — large preview, name, kind, tags. Scroll down into the tools: they appear by the type of whatever you selected, with params, preview, confirm, and undo in one line.

Eleven built-in tools, four domains

Images (convert / resize / rotate & flip / remove background) · PDF (merge / compress / extract pages) · audio & video (transcode / extract audio) · text (encoding convert / JSON format).

Products go through the engine too

Tools aren't a side door — every product lands via preview → confirm → ⌘Z; collisions yield automatically, and only the engine ever touches originals.

Playable up top

In the window above: select two photos → Convert Format → Preview → Confirm → ⌘Z. Fully live. Demo data; the decision logic mirrors the app.

Convert Format PNG · JPEG · HEIC

Format segment, EXIF toggle, output name (an edited name keeps the stem — the extension always follows the format), target directory — every step is the app's own step.

Resize 16–10000 px

Width and height linked by an aspect lock; the default product name derives from the width. Multi-selection derives per file — nothing overwrites.

Preview → Confirm

The op list reads from → to, line by line; confirming rides the existing progress, toast, and sound — ⌘Z reverts the whole batch, same channel as moves, copies, renames.

The workbench saves
a place for you.

An .sfplugin is a single-file plugin: a declared manifest plus an entry script in any stack — bash, Python, Node. Import it in settings; it mounts in the sidebar's tools area.

Two modes, both through the engine

plan emits an operation table (whitelisted: rename / move / mkdir); transform emits staged products — either way, the only path to disk is the pending-ops engine: preview → confirm → undoable.

Subprocess + ledger

Plugins run in their own process group over a stdin/stdout JSON contract; output caps, a timeout ladder, out-of-bounds rejection, and orphan-staging sweeps are all built in.

The official dev Skill

Export it from settings — manifest spec, the contract doc, two example plugins (bash / Python), and a standalone validator. Let an AI agent write plugins for you.

An honest boundary

Plugins are code you installed yourself: their networking is unrestricted and the responsibility is yours. The app's own code contains no networking — a statement of fact, not a setting.

Fast, but never out of bounds.

What got browser-ified is the operating, not the boundaries.

Trash is the only exit no permanent delete

Deletion always goes to the system Trash. There is no path around it inside the app. Not a default — an invariant.

No account. No cloud. No telemetry.

The app's own code contains no networking and no analytics. External plugins are user-installed code — their networking sits outside the app's boundary, responsibility and all. Neither does this site (zero third-party requests).

Every write action undoes full audit trail

Moves, copies, renames, tool products take effect immediately; ⌘Z reverts silently — and every write lands in an auditable ledger. That ledger is watched by 1,947 unit tests; every number drills down to the file it comes from. The Finder-parity basics — batch rename, Space for Quick Look, ⌘1–4 views — are all here too; they're just not the reason this workbench exists.
